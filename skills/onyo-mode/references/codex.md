# Codex compatibility for ostack

ostack is a first-stage harness port of pstack 0.15.32 at `99b609a72323b70204eab407c622f436e858e112`. Active branding uses `onyo-mode`, `onyo-help`, `setup-ostack`, and `onyo-agent`, while preserving inherited planning, research, routing, project coordination, approval gates, and execution workflows. User-approved product selection omits nine skills and the dormant Benny pack, as recorded in the source checkout’s `sync/omissions.json`; associated reference cleanup uses `[P]` patches rather than harness-only `[A]` patches. It does not add a planner or replace orchestration. The old ostack Claude hooks and onyo-projects workflow are not included. Text and schema checks do not establish runtime completeness.

Read this mapping before using a skill. A workflow instruction does not grant permissions beyond the user's request or the host's policy. Keep an unmet gate visible as blocked; never count unavailable runtime proof as a pass.

## Reading packaged resources

Filesystem installs and cloud skill readers expose the same instructions through different locators. On a filesystem, resolve Markdown links from the containing file, following symlinks to the installed skill. In a cloud skill reader, use the package for the owning skill and its complete resource URI. Derive the installed plugin owner from a URI actually returned by the reader; do not guess it from a marketplace name or reuse another plugin’s owner.

For example, when the reader returned `skill://<installed-owner>/arena/SKILL.md`, compatibility is in the `onyo-mode` package at `skill://<installed-owner>/onyo-mode/references/codex.md`. Replace the placeholder with that returned owner. Read a sibling skill from its own package, even when it is absent from the implicit skill catalog. Read a subfile such as `references/explorer-prompt.md` from that skill’s package, preserving its full within-skill path. A directory link names its `README.md` index where provided. Use the reader’s current contract for package and resource arguments; the URI is not a shell path.

Canonical shared resources are `onyo-mode/references/codex.md`, `onyo-mode/references/onyo-agent.md`, `no-comments/references/comment-sicko.md`, and `onyo-help/references/guide/`. The source repository’s compatibility page points here. There are no runtime reads of repository-root `docs/` or `agents/` resources. Delegates receive either a verified filesystem locator or the owning cloud package plus resource URI and the instructions required by their role.

A readable resource does not prove executable files were materialized. Scripts, Git trunk reads, and runtime verification still need the host’s actual filesystem, execution, history, and control capabilities. Use available authorized facilities or report the required step blocked; do not pass a `skill://` URI to `node`, `git`, or a file reader. Likewise the packaged resource reader does not expose the user’s `$CODEX_HOME/pstack-models.md`; use an authorized host reader or supplied settings and disclose unavailable configuration access. Do not silently infer that an inaccessible file is absent. Reading GitHub source is not proof that the installed resource is readable.

## Tools and roles

The following native-subagent names were observed in this porting session, not promised as universal Codex APIs or cloud-task controls. Inspect the current exposed schema before calling tools. Orchestrate’s isolated cloud-task path is described separately below.

| Upstream requirement | Codex mapping and limit |
| --- | --- |
| `Task` | Native `collaboration.spawn_agent` with `task_name` and `message` in this surface. Calls are asynchronous. Read terminal results and review the work. |
| Resume/message/status/wait | `followup_task`, `send_message`, `list_agents`, `wait_agent`, and `interrupt_agent` where exposed. A follow-up can start work; use a read-only status check for liveness. Preserve pstack's fresh-agent and narrow reuse rules. |
| `subagent_type` | Configured custom agent when the client supports selection, otherwise read the [Onyo wrapper](onyo-agent.md) from the `onyo-mode` package or [Comment Sicko wrapper](../../no-comments/references/comment-sicko.md) from the `no-comments` package and include its instructions in the brief. A task name does not load a role. |
| `readonly` | Explicit no-edit scope plus output/diff review. Parent permissions are inherited; no new sandbox is implied. |
| `run_in_background` | Omit. Native spawning here already returns asynchronously. |
| `environment`, `cloud_base_branch` | No native equivalents in the exposed spawn schema. Worktree setup is explicit. Isolated/durable cloud execution remains a separate requirement. |
| `AskQuestion` | `request_user_input` only when exposed and permitted by the current mode; `request_user_input_async` where exposed, otherwise a plain-text question. Preserve approval gates. |
| File read, Shell, Grep | Exposed shell execution (`exec_command` here), file tools, and `rg`. These are operations, not invented universal tool names. |
| Todo list | Use an exposed plan tool if available, otherwise maintain the same ordered checklist in the conversation or project artifact. This does not add a planning workflow. |
| MCP discovery | Inspect the exposed tools and discover authorized sources. No assumed Cursor `mcps/` directory. |

Native subagents share this selected execution environment. They are not durable cloud tasks, do not get their own VM or worktree automatically, and cannot be assumed to survive a parent restart. Codex cloud is a separate product surface. Orchestrate uses ChatGPT Spaces/Pages for its durable project record as described below. That storage does not supply persistent coordinator execution. Orchestrate uses the coordinating parent’s exposed Codex cloud-task controls where available; this repository supplies no implementation of those controls. Missing placement, status, result or wake capabilities remain gaps, not reasons to substitute native subagents.

## Models, installation, and configuration

Install **ostack** through the desktop app’s Plugins Directory as described in the [setup guide](../../onyo-help/references/guide/01-setup.md). This branch supplies `.agents/plugins/marketplace.json` and the supported `.codex-plugin/plugin.json` compatibility manifest. The marketplace’s `./` source keeps the existing repository-root skills and their sibling files together in the installed copy. Use the `codex` branch when importing this repository as a marketplace source. The app manages the installed copy; references and scripts remain relative to the plugin root. See the [official packaging documentation](https://developers.openai.com/plugins/build/plugins). Explicit Codex invocation uses `$skill-name`. Remaining `/skill-name` spellings in upstream workflow prose are skill labels: load that skill by name/path or use `$skill-name`, not an invented Codex slash command. `/loop` is an exception and remains an unsupported wake dependency.

Upstream `disable-model-invocation: true` is represented by `agents/openai.yaml` with `policy.allow_implicit_invocation: false`. `icon` and `color` frontmatter are removed from skill files; no equivalent visual behavior is claimed. Other skills keep upstream invocation policy. No always-on hook is installed.

Historical archives, upstream source paths and licensing retain pstack names. Internal tooling identifiers (`@cursor-skill/poteto-mode-tools`, `.poteto-mode-tools-install-key`, `PSTACK_TRANSCRIPTS_DIR`, and the sync cache setting) remain unchanged for compatibility; they are not active skill names.

Custom agent definitions remain in `.codex/agents/*.toml` as supporting source files. Their matching Markdown role bodies are [Onyo's `references/onyo-agent.md`](onyo-agent.md) in the `onyo-mode` package and [Comment Sicko's `references/comment-sicko.md`](../../no-comments/references/comment-sicko.md) in the `no-comments` package. The plugin manifest declares skills; it does not claim to install or register custom agents. In clients whose exposed spawn tool cannot select a configured role, include the packaged Markdown instructions in the brief. Runtime loading of the TOML definitions has not been tested in this environment.

`$setup-ostack` preserves the 15 retained role keys, budget/confirmation sequence, and panel counts. It writes user-level `$CODEX_HOME/pstack-models.md`, which workflows read explicitly. `pstack-models.md` is the legacy configuration filename retained for backward compatibility; branding does not migrate or rename user files. Resolve `CODEX_HOME` from the host environment, defaulting to `~/.codex`, so the default path is `~/.codex/pstack-models.md`. This preserves upstream user-level scope without adding a repository override hierarchy. This is an ostack data file, not native Codex config or an always-applied rule. Native configuration uses `.codex/config.toml` or `~/.codex/config.toml`; this port does not modify either.

Model IDs and reasoning effort are separate. Use only exposed supported choices. In this session, `model` and `reasoning_effort` overrides require `fork_turns: "none"`; full-history forks inherit. The ostack aliases `auto` and `inherit-parent` mean omit overrides, not model IDs. The user-selected mapping replaces upstream Opus 5.5 defaults with `gpt-6.1-sol` and Grok 4.7 defaults with `gpt-6.1-terra`. All 15 retained roles and panel counts remain. Without a recorded budget, medium/high is the starting choice; saved or explicitly selected budgets, including large/xhigh and unlimited/max, take precedence. The selected budget supplies each real model’s starting effort; the original task-level adjustments remain relative to it. These IDs were confirmed in the selecting host, not universally entitled: detect support again in the invoking host and mark unavailable setup choices for confirmation. There is no claimed equivalent for upstream cross-family diversity or suffix-based speed settings. Panel seats remain independent, but same-model reviews do not satisfy cross-family diversity. Report that semantic limitation explicitly.

## Orchestrate records in Spaces

The [Orchestrate playbook](../playbooks/orchestrate.md) uses Hsit/dot as the planning/routing coordinator and one authoritative project Page/index as its durable record. This names the coordinator role, not a private dot API. Current records are read before dispatch and reconciliation; scope changes, decisions and verified reports are saved through guarded updates. Workers receive self-contained briefs and return source-linked reports without needing Pages or shared filesystem access.

Native headings, checklists, tables and links hold unit IDs, upstream dependency context, branch/PR mappings, exact SHAs, verifier evidence, user gates, status and observed frontier snapshots. The coordinator reconciles these with the actual forge/task state; Pages do not calculate readiness or become live GitHub truth. A changed head invalidates verification. The inbox holds completion pointers. Preserve source reports and tool receipts while reconciling partial or uncertain saves, with tool-required guards and readback. This path adds no mandatory versioning, dependency-ID schema, event identity, or processed-event register. Single-writer ownership is a coordination convention, not a distributed lock. Preserve user edits and existing privacy; never store secrets or raw sensitive logs.

The existing `scripts/orch/` implementation still operates on local files. It is optional legacy/local tooling, not a Pages backend, and is not invoked by this Spaces path. No connector, new planner, scheduler, automatic edit-trigger subscription, or autopilot redesign is included. The cloud-task lifecycle below adapts the existing worker workflow without implementing infrastructure. Small-task collapse and all planning/review/acceptance gates remain.

Capability documentation checked on 2026-10-25: the active Pages plugin's `write-page` and `maintain-space` skills, `write-page/references/page-content.md`, and `write-page/references/edit-requests.md`, plus exposed `read_page`, `edit_page`, `patch_page`, and `create_page` tool descriptions. The skill package is `skill://plugin_connector_1p_4a72ddeef4c481918f92d8e8df18fb2c`. These document native formatting, read-derived block guards, per-operation receipts and recovery; they do not establish transactional multi-page writes. Consult the coordinator's current skills/tools for exact arguments. No user Page was read or changed to validate this repository port, and live persistence/access remains untested.

## Orchestrate cloud-task lifecycle

The parent assistant creates isolated Codex cloud tasks, retains their returned references, and reads status/results through its active task controls. Workers return their existing report in the final response; they generally have no parent-messaging API. Terminal callbacks from parent-created tasks are observed in the coordinating surface and feed the existing completion inbox. The parent still reads the report and verifies its SHA and evidence. A terminal turn is not proof of acceptance.

User-created or adopted tasks do not have a universally verified wakeup path. Nor does a restart prove that a callback relationship survives. During recovery the parent reads known tasks and reconciles their PR/branch state; reading is not a subscription or a continuation turn. Preserve upstream retry limits, timeboxes and fresh-worker defaults. Continue a returned task only under the existing narrow state-preservation exception and an available continuation control. Watcher wakeups and nested cloud-task controls remain capability gaps where unavailable; no retry scheduler or heartbeat protocol is added.

Evidence boundary on 2026-10-25: the coordinating parent reported observed parent-created terminal callbacks and parent-side result reads. This delegated execution environment receives task instructions and returns final results, but its exposed tool catalog does not include the parent's cloud-task creation/read schemas. Accordingly this port specifies those operations by capability and requires the parent's current tool contract; it does not invent method names, arguments, callback subscriptions or a child-to-parent send tool. This change did not run a new cloud-task lifecycle test.

## History access for Session pickup

Use only authorized project-scoped history directly readable by the invoking/coordinating agent, such as managed cloud or local task IDs, or explicitly user-supplied handoffs/exports, inspecting their actual formats. A standalone local agent may use its own exposed reader; this is not a cloud-only boundary. Do not spawn intermediary agents merely to retrieve otherwise inaccessible conversations or use filesystem discovery/database crawls as a workaround. Never bypass explicit access denial. Missing direct access is a coverage gap, not a trigger for multi-agent retrieval. Titles and summaries identify candidates; they do not prove actions. A supplied state capsule can make history mining unnecessary. If sources are unavailable or incomplete, say so and retain the playbook's live-artifact checks.

The coordinating parent's supplied local tool contract, checked on 2026-10-26, exposes `mcp__codex_app__list_threads(limit)` for bounded discovery metadata, with no query or cursor. Filter returned metadata locally. Do not claim exhaustive coverage, project membership, or recency when the result does not establish them. `mcp__codex_app__read_thread(threadId, hostId?, cursor?, turnLimit?, includeOutputs?, maxOutputCharsPerItem?)` reads a known thread; follow returned cursors as needed with `turnLimit <= 10`. It returns summaries and optional outputs, not guaranteed lossless history. Disclose omitted or truncated evidence; a summary does not replace missing tool results. Inspect the runtime schema before calling: these are host-specific contracts, not universal full-text search APIs.

Parent-side cloud listings and paginated reads are usable only where those controls are exposed. Cloud workers tested by the parent lack both the local reader and parent cloud-thread controls; do not assume that access or arrange an agent relay to work around its absence. Do not use `global_search` as a substitute for Codex history. Archived threads may appear through an exposed archived listing, but retained or deleted history is never assumed. This mapping uses the parent's supplied tool evidence; this repository change did not scan private history.

## Remaining compatibility gaps

- **Wake and custom modes:** no verified equivalent for Cursor's `/loop`, Option/Alt+Enter Custom Modes, restart-persistent coordinator, or cloud nesting guarantees in this surface. Preserve the predicate and wake requirement; report unattended steps blocked without a verified facility.
- **Transcripts:** Session pickup uses the [available history sources](#history-access-for-session-pickup); no universal transcript layout or complete history is promised. Do not assume Cursor paths or search unrelated sessions. `worktree-audit.sh` accepts `PSTACK_TRANSCRIPTS_DIR`; without it LAST_CHAT evidence is unavailable. Never infer liveness from transcript mtime.
- **External skills:** `cursor-team-kit` deslop/control skills and Cursor's authoring skill are not bundled Codex tools. Use an available compatible skill or the workflow's stated review/proof method. Missing evidence remains a gap.
- **Hooks:** Codex has documented hooks. The prior fork's Claude-only hooks are excluded by scope, not because Codex lacks all hook support.
